# 奥术王座(fantasy-card-battle)维护指南

> 目标读者:没有任何上下文、首次接手本项目的开发者或 AI 模型。读完本文即可定位代码、安全地加卡牌/改规则。

## 1. 项目概览

- **是什么**:一个炉石传说风格的单机卡牌对战网页游戏(玩家 vs 内置 AI),全中文界面。
- **技术栈**:React + Vite,无路由、无状态管理库、无 UI 库、无测试框架。
- **持久化**:仅 `localStorage`(键 `arcane-deck`,存玩家自组的 30 张牌组)。
- **运行**:
  ```bash
  npm install
  npm run dev      # 开发
  npm run build    # 构建到 dist/
  npm run preview  # 预览构建产物
  ```

## 2. 文件结构

| 文件 | 作用 |
|---|---|
| `index.html` | 入口 HTML |
| `src/main.tsx` | React 挂载入口 |
| `src/FantasyCardBattle.tsx` | **整个游戏**:卡牌数据、规则引擎、AI、全部 UI(约 1500 行) |
| `src/styles.css` | 少量全局样式(大部分样式是组件内联 style + 文件内 `CSS` 字符串里的 keyframes) |

⚠️ 已知状态:代码是**无类型 JS 写在 .tsx 里**,项目没装 `@types/react`,IDE 会报大量 implicit-any / JSX 类型错误——这是既有现状,Vite 构建不做类型检查,**不影响构建与运行**,不要被这些诊断误导。

## 3. `FantasyCardBattle.tsx` 内部分区(按文件顺序)

### 3.1 卡牌数据区(文件头部)

- `POOL`:全部可入牌组的卡。`COIN`(id 99,幸运币)和 `GHOUL`(id 98,食尸鬼)是 **token 衍生牌**:带 `token: 1`,不进 `POOL`(因此不出现在牌组构建器),单独注册进 `byId`。
- `byId`:id → 卡牌定义的全局索引,引擎各处用它查卡。
- 卡牌字段:

| 字段 | 含义 |
|---|---|
| `type` | `"m"` 随从 / `"s"` 法术 |
| `atk` / `hp` | 随从攻击/生命 |
| `taunt` / `charge` | 嘲讽 / 冲锋 |
| `aura` | 在场光环,目前仅 `"cheapSpells"`(伊谢尔:法术费用变 1,见 `effCost`) |
| `bc` | 战吼,目前仅 `{ k: "summonMini" }`(巴内斯),见 `doBattlecry` |
| `sp` | 法术效果定义,见下表 |
| `token` | 衍生牌标记,不可入牌组(`loadPlayerDeck` 会拒绝) |

- `sp.k` 效果种类一览:

| `sp.k` | 效果 | 附加字段 |
|---|---|---|
| `dmg` | 单体伤害(吃法伤加成) | `n` 伤害;`t` 目标;`draw` 附带抽牌;`armor` 附带护甲;`summon` 附带召唤(填 token 卡 id,如终极感染的食尸鬼 98) |
| `aoe` | 敌方全体伤害(吃法伤加成) | `n` |
| `heal` / `buff` / `draw` | 治疗 / 随从增益(`a`/`h`)/ 抽牌 | |
| `coin` / `bio` / `obelisk` | +1 临时法力 / 双方+2 水晶 / 本回合法伤+1 | |
| `choose` | 通用二选一抉择(鼓舞、滋养) | `opts: [{fx, n, emoji, label}]`,效果见 `applyOpt` |
| `camp` | 星夜露宿,抉择三次 | 选项硬编码在 `campEffect`/`campLabel` |
| `bloom` | 夜影花蕾,两步抉择(选模式→选牌) | |
| `moonlight` | 月光指引【发现】 | 复制机制见 `gainMoonCopy`/`moonTutor` |

- `sp.t` 目标类型:`"any"` 任意角色 / `"fm"` 友方随从 / 缺省 = 无目标(校验在 `isValidSpellTarget`)。

### 3.2 规则引擎(纯函数区)

所有引擎函数签名形如 `fn(st, side, ...)`:直接修改传入的 state 对象 `st`,`side` 为 `"p"`(玩家)或 `"a"`(AI)。**引擎不碰 React**。

- state 形状:`{ phase, turn, turnNum, winner, fx, logs, notice, pending, banner, p: {...}, a: {...} }`;
  每方:`{ hp, armor, mana, maxMana, fatigue, spellDmg, deck: cid[], hand: {uid, cid, moon?}[], board: minion[] }`。
- 关键函数:`draw`(含疲劳/烧牌)、`dmgHero`(护甲先扣)、`dmgMinion`、`startTurn`、`playMinion`、`castSpell`、`castDeckSpell`、`dmgExtras`、`resolveAttack`、`effCost`(光环减费)、`gainMana`。
- ⚠️ **法术施放有两条路径,改效果必须两处同步**:
  - `castSpell`:从手牌打出(玩家与 AI 共用,有明确目标);
  - `castDeckSpell`:从牌库直接施放(夜影花蕾翻出的法术,目标随机、抉择随机)。
  - 伤害法术的附带效果(抽牌/护甲/召唤)已抽到 `dmgExtras` 共用,新加附带效果优先扩展它。
- **法伤系统**:`side.spellDmg` 由魔法方碑设置,`startTurn` 时**双方都清零**(即只持续当前回合);`dmg`/`aoe` 实际伤害 = `sp.n + spellDmg`。
- **法伤的牌面显示是纯展示层**:`spSummary(sp, bonus)` 与 `cardDesc(c, bonus)`(数据区底部)在 `bonus > 0` 时把伤害数字渲染成 `* n *` 形式;真实数值仍只在引擎里计算。显示接入点:手牌(`HandCard` 的 `bonus` prop)、卡牌预览面板、抉择弹窗的牌库卡。

### 3.3 AI(`aiPlay` / `aiAttack` / `computeAiTurn`)

- `aiPlay` 是一条**优先级 if-return 链**(开方碑→斩杀→AOE 清场→点杀→治疗→各种抉择牌→铺场→……),每次只做一个动作,返回是否有动作。
- 抉择类法术 AI 不走弹窗:`aiPlay` 内直接按启发式选项结算(注意这些分支是**手动扣费+splice 手牌**,没有走 `castSpell`)。
- `computeAiTurn`:克隆 state → 跑完整个 AI 回合 → 产出**快照数组**;UI 层以 750ms 间隔依次 `setGame` 回放,形成"AI 一步步出牌"的动画效果。⚠️ AI 回合期间不要另行 `setGame`,会被后续快照覆盖。

### 3.4 UI(`ArcaneThrone` 组件)

- `game.phase`:`menu`(主菜单)/ `deck`(牌组构建)/ `play`(对战)/ `over`(结算)。
- 状态更新统一走 `mutate(fn)`:深拷贝当前 state → `fn` 内用引擎函数修改 → `setGame`。
- 展示组件(`Badge`/`MinionEl`/`HeroEl`/`HandCard`)定义在**模块顶层**,避免每次渲染重挂载导致 transition 失效——新增展示组件请保持这个写法。
- 浮动数字(`fx`)、战斗记录(`logs`)、重要提示(`notice`)、回合横幅(`banner`)各有独立渲染块。

### 3.5 pending(抉择弹窗)系统 ⭐ 本项目最容易改坏的部分

`st.pending` 非空时弹出全屏抉择层,**并阻断其余全部交互**(`handleHand`/`clickEntity`/`endTurn` 开头都检查 `game.pending`)。

| `pending.k` | 来源 | 可取消? | 支付时机 |
|---|---|---|---|
| `choose` | 鼓舞/滋养 | ✅ | **延迟**:确认选项时(`pickChoose`)才扣费、移出手牌 |
| `bloomMode` | 夜影花蕾第一步(选召唤/施法) | ✅ | **延迟**:确认模式时(`pickBloomMode`)才支付 |
| `bloomPick` | 夜影花蕾第二步(已翻开牌库 3 张) | ❌ | 已在上一步支付 |
| `moonPick` | 月光指引【发现】(已翻开牌库 3 张) | ❌ | 进入弹窗前支付 |
| `camp` | 星夜露宿(抉择三次,`remaining` 计数) | ❌(多次抉择) | 进入弹窗前支付 |

**延迟支付设计**:可取消的两类在进入弹窗时**不扣费、不离手**,`pending` 里只存手牌索引 `i`;确认时才 `mana -=`、`hand.splice`、触发 `moonTutor`;取消(`cancelPending`)只需 `pending = null`。
该设计成立的前提是 **pending 期间手牌不可能变化**(交互全被阻断),因此索引 `i` 不会失效——如果将来加入"pending 期间也能发生的效果"(如回合计时器自动出牌),必须先重构这里。

**不可取消的原因**:`bloomPick`/`moonPick` 已向玩家展示了牌库内容,允许取消等于"免费偷看牌库 + 重新随机刷选项"。

### 3.6 月光指引(moon)机制

- 发现的复制进手牌时带 `moon: turnNum`(`gainMoonCopy`)。
- 任何"从手牌打出"的路径(`playMinion`/`castSpell`/各抉择确认函数)结尾都要调 `moonTutor(st, side, en)`:若打出的是本回合的 moon 复制,则从牌库定向抽本体。**新增任何"从手牌打出"的路径都不要漏掉这一行。**

## 4. 如何添加一张新卡(checklist)

1. `POOL` 加条目,id 唯一;若是 token 衍生牌则不进 `POOL`,定义常量后 `byId[X.id] = X`。
2. 复用现有 `sp.k` 的话到此为止;若新增 `sp.k`,需要同步:
   - [ ] `castSpell`(手牌施放路径)
   - [ ] `castDeckSpell`(夜影花蕾可能从牌库翻出它)
   - [ ] `isValidSpellTarget`(无目标法术要加进白名单那一行)
   - [ ] `spSummary`(手牌角标简述);伤害类还要确认 `cardDesc` 的法伤显示
   - [ ] `aiPlay`(AI 牌库也是随机生成的,**AI 一定会抽到这张卡**,必须有使用逻辑,否则 AI 会卡手)
   - [ ] 若需要玩家交互弹窗:`handleHand` 加分支 + `pending` 新 k 值 + 弹窗渲染 + 确认/取消函数
3. 手动测试三条路径:玩家打出、AI 打出、被夜影花蕾从牌库直接施放。

## 5. 常见坑

- `clone` 用 `JSON.parse(JSON.stringify())`:state 里**不能放函数、undefined、Date**。
- `UID`/`FXID` 是模块级自增全局变量,HMR 热更新后继续累加,不要假设从 1 开始。
- 数值规则:手牌上限 8(超出烧牌)、随从区上限 6、牌库抽空后疲劳递增、英雄血上限 30、法力上限 10。
- `summonFromDeck(st, side, cid)` 名字有误导:它**不从牌库移除**,只是按 cid 把随从放上场(需要移除时调用方自己 `removeFromDeck`)。终极感染召唤食尸鬼也是直接用它。
- 战吼(`bc`)只在从手牌打出时触发(`playMinion`),从牌库召唤(`summonFromDeck`)不触发——这是有意为之。
- AI 的抉择牌分支在 `aiPlay` 里手动扣费,与玩家路径(延迟支付)实现不同,改抉择规则时两边都要看。

## 6. 架构建议(按优先级)

当前"单文件 + 无类型 + 无测试"在 1500 行规模已到可维护性临界点。建议按下面顺序演进,每步独立可落地:

1. **拆文件**(收益最大、风险最低):`cards.ts`(POOL/token/byId)→ `engine.ts`(规则引擎纯函数)→ `ai.ts` → `ui/` 组件若干。引擎本来就不碰 React,拆出来是纯搬运。
2. **补上 TypeScript**:装 `@types/react`,给 `Card`/`SpellDef`/`GameState`/`Minion`/`Pending` 建 interface。`sp.k` 改成 discriminated union 后,上面 checklist 里"漏改一处"的错误会变成编译错误。当前满屏 any 诊断也会消失,IDE 才能真正帮上忙。
3. **效果注册表替代 switch 分发**:`sp.k` 目前在 `castSpell`/`castDeckSpell`/`isValidSpellTarget`/`spSummary`/`aiPlay` 五处重复分发,"加一张卡改五处"是本项目最大的结构性成本。改成 `effects[k] = { cast, autoCast, validTarget, summary, aiScore }` 注册表,新卡只写一个对象。
4. **随机数可注入**:`Math.random` 直接散落各处,无法写可复现的测试。引擎函数统一从 `st.rng()` 取随机,初始化时注入带种子的 PRNG。
5. **给引擎加单测**(依赖第 4 步):引擎是纯函数,用 vitest 测试成本极低。最值得覆盖:疲劳/烧牌、嘲讽规则、法伤加成、抉择延迟支付(取消不扣费)、月光指引复制链。
6. **动画与逻辑解耦**:AI 回合的"快照数组 + setTimeout 回放"在引入连锁效果、亡语等机制后会失控。建议引擎产出**事件流**(`[{type:"draw"...},{type:"damage"...}]`),UI 消费事件做动画队列——这也顺带解决 `fx` 浮字与逻辑耦合的问题。
7. **状态更新**:JSON 全量深拷贝在当前规模没问题;若 state 变大(如战斗回放、观战),考虑 immer 或手写浅拷贝。
8. **样式**:内联 style 占了文件近半行数,拆组件时可顺手迁移到 CSS Modules;但不必为迁而迁。
9. **内容外置**:平衡性调整频繁的话,把 `POOL` 移到 JSON/TS 数据文件,改数值不碰逻辑。
